# DHC 沉睡客戶「真復活」預測

> BDA2026 期末專案 — 91APP shop#3（DHC 保健食品）回流客戶價值分層
> 2026-06-03

## 專案目標

保健食品客戶會週期性補貨、也會週期性沉睡。當一位沉睡客戶**重新下單（t₀）**時，
品牌需要判斷：這是會持續回購的「**真復活**」，還是買完即走的「**路過**」？

**標籤定義**：t₀ 之後 **120 天觀察窗**內若有 ≥1 次後續購買 → `y=1`（真復活），否則 `y=0`（路過）。

分辨出這兩種客戶,才能把行銷預算精準投到「推一把就會留下」的中間客群,避免浪費在注定路過
或本來就會留下的人身上。

## 為什麼選 shop#3（DHC）

| 理由 | 數據支撐 |
|------|---------|
| 消耗品 → 反覆沉睡再回流,天然的預測題 | 偵測到 511,800 個回流事件,平均每位活躍會員 1.49 次 |
| 購買有清晰節奏,可建模 | 全體購買間隔中位數 67 天 |
| 資料量足以支撐 ML | 有效訂單 465 萬筆、會員 108 萬人（全資料集約 1/5） |
| 回流率高、行銷可介入空間大 | 整體真復活率 62%,個體差異大 → 值得分層 |

## Pipeline

從 1,147 萬筆原始訂單（91APP 全資料集）產出 287,824 筆帶標籤的回流樣本,四個階段:

| 階段 | 腳本 | 主要產出 |
|------|------|---------|
| 1. 前處理 | `preprocess_shop3.py` | 樣本骨架、`output/data_preprocessing.md`、`output/pipeline_report.md` |
| 2. 特徵工程 | `feature_engineering.py` | 57 個特徵、`output/feature_engineering.md`、`output/feature_sanity.md` |
| 2.5 清理 | `clean_features.py` | 修正 `age_at_t0` / `days_since_register` 壞值 |
| 3. 建模 | `modeling.py` | `output/model/xgb_model.json`、`output/model/metrics.md`、SHAP |
| 4. 分析 | `analysis.py` | `output/model/results_analysis.md`、無快照對照模型、機率校準分析 |

### 關鍵設計:零洩漏的時序管線

- **動態個人購物週期 Cᵢ**:每位客戶的沉睡門檻是 `clip(3 × Cᵢ, 30, 365)` 天,Cᵢ 只用該次購買**之前**的歷史估算,不偷看未來。
- **三重防洩漏切分**:標籤窗用精確時間戳記排除 t₀ 訂單本身、censoring 剔除觀察窗超出資料截止日的樣本、train/test 之間留 120 天 embargo 緩衝。

| Split | 樣本數 | t₀ 範圍 | 真復活率 |
|-------|-------:|---------|--------:|
| train | 198,370 | 2022-02 ~ 2023-03 | 67.1% |
| test  | 89,454  | 2023-07 ~ 2023-11 | 56.5% |

### 特徵（6 組,共 57 個）

| 組 | 數量 | 主題 |
|----|-----:|------|
| F1 | 17 | 歷史 RFM 與行為穩定性 |
| F2 | 12 | t₀ 訂單本身 |
| F3 | 7 | 商品行為 |
| F4 | 8 | 會員背景 |
| F5 ⭐ | 8 | 跨期交互（真復活 vs 路過的主要判別訊號） |
| F6 | 5 | 近期活躍窗口 |

## 模型與結果

XGBoost 二元分類,第一版使用預設參數,不調超參。

| 指標 | train | test |
|------|------:|-----:|
| AUC-ROC | 0.827 | **0.742** |
| AUC-PR | 0.911 | 0.809 |
| Precision / Recall (@0.5) | 0.81 / 0.85 | 0.69 / 0.76 |

### 洞察一:自我攻擊驗證,證明模型沒有依賴洩漏

SHAP 重要性第一名的 `member_card_level` 是會員快照欄位,可能反映 t₀ 之後的狀態（疑似前向洩漏）。
把三個快照欄位移除重新訓練後,**AUC 只掉 0.027**——證實該資訊可由合法的購買歷史重建,模型並非
依賴洩漏在作弊。乾淨版模型（`output/model/xgb_model_no_snapshot.json`）作為可上線基準。

### 洞察二:35.7% 的客戶落在可被行銷影響的中機率帶

| 機率層 | 人數 | 佔比 | 實際真復活率 |
|--------|-----:|----:|----:|
| 高 (>0.6) | 42,527 | 47.5% | 0.76 |
| **中 (0.4–0.6)** | **31,952** | **35.7%** | **0.41** |
| 低 (<0.4) | 14,975 | 16.7% | 0.34 |

中機率帶是行銷主戰場,但模型在此帶系統性高估（實際 0.41 而非 0.5）,源於 train/test 的
留存率下滑（67%→57%）,上線前需做機率校準（Isotonic/Platt）。

### 洞察三:灰色地帶裡的判別訊號

即使機率模稜兩可,中機率帶內「沉睡較短、近一年仍活躍、歷史訂單多、非一次性買家」的客戶
明顯更會真復活,可直接作為行銷觸發條件。

完整分析見 [`shop3_final.md`](shop3_final.md)（提案重點）與 [`output/final_report.md`](output/final_report.md)（全流程總報告）。

## 專案結構

```
├── preprocess_shop3.py      # 階段1: 前處理(篩選 shop#3、動態 Cᵢ、防洩漏切分)
├── feature_engineering.py   # 階段2: 特徵工程(57 個特徵)
├── clean_features.py        # 階段2.5: 壞值清理
├── modeling.py               # 階段3: XGBoost 建模 + SHAP
├── analysis.py                # 階段4: 快照消融實驗、機率校準、SMD 分析
├── EDA.py                     # 探索性資料分析
├── shop3_final.md             # 提案重點(給非技術讀者)
├── bda2026_final_proposal.pdf # 原始提案
├── Prompt/                    # 各階段使用的 LLM prompt 紀錄
└── output/
    ├── *.md                   # 各階段報告
    ├── s3_*.png                # EDA 圖表
    └── model/                  # 訓練好的模型、SHAP 圖、評估指標
```

## 關於資料

本 repo **不包含**原始 91APP 資料集（會員/訂單/商品頁,約 19GB,含真實客戶交易紀錄）與衍生的
完整特徵表（`train_features.csv` / `test_features.csv`）,僅保留程式碼、文件與模型產出,
避免外洩課程提供的專有資料。若要重跑 pipeline,需自行準備符合相同欄位格式的 91APP 資料集。
